## Overview

### Introduction

GitHub Metrics Aggregator (GMA) is a GitHub app that ingests events from the GitHub API to create dashboards about development velocity and productivity. It provides a robust and resilient data ingestion pipeline, ensuring that GitHub events are reliably captured and stored in BigQuery for analysis.

The system is composed of a real-time webhook ingestion service and several asynchronous background jobs for data processing, retries, and compliance.

### Architecture

The system is designed around a decoupled, event-driven architecture.

!["Architecture Diagram"](./assets/architecture.png)
*(Note: The original `architecture.svg` has been converted to `architecture.png` for broader compatibility, as requested.)*

The high-level data flow is as follows:
1.  **GitHub** sends webhook events to the **Webhook Service**.
2.  The **Webhook Service** validates the events and publishes them to a **Pub/Sub Topic**.
3.  A **BigQuery** sink subscribes to the Pub/Sub topic and streams the events into a raw events table.
4.  Asynchronous **Cloud Run Jobs** (Retry, Artifact, Review) are triggered on a schedule to perform additional data processing, enrichment, and ensure data integrity.
5.  All components are defined as code using **Terraform**, and deployment is managed via **GitHub Actions**.

### System Components

The application is broken down into four main components:

#### 1. Webhook Service

-   **CLI Command:** `webhook server`
-   **Purpose:** This is the primary, real-time ingestion point for all GitHub events. It's a public-facing HTTP server that listens for webhook pushes from a configured GitHub App.
-   **Logic:**
    -   Receives and validates incoming webhook payloads using a shared secret.
    -   Publishes the raw event payload to a Pub/Sub topic for initial ingestion.
    -   If publishing fails, it has a built-in retry mechanism. After a configured number of retries, it sends the event to a Dead-Letter Queue (DLQ) topic.
    -   It records failed delivery attempts in a dedicated BigQuery table to provide observability into ingestion issues.

#### 2. Retry Job

-   **CLI Command:** `job retry`
-   **Purpose:** To ensure eventual consistency and data completeness, this job finds and re-delivers webhook events that GitHub failed to deliver to the webhook service.
-   **Logic:**
    -   Runs as a scheduled Cloud Run Job.
    -   Uses a Google Cloud Storage (GCS) lock to prevent concurrent runs.
    -   Authenticates to the GitHub API as the GitHub App.
    -   Queries the GitHub API for the recent history of webhook deliveries.
    -   It keeps track of the last successfully processed delivery via a "checkpoint" stored in BigQuery, so it doesn't re-process the entire history on each run.
    -   If it finds any deliveries that failed (non-2xx status code), it triggers a redelivery via the GitHub API.

#### 3. Artifact Job

-   **CLI Command:** `job artifact`
-   **Purpose:** This is a data enrichment job that fetches and stores detailed logs from GitHub Actions workflow runs.
-   **Logic:**
    -   Runs as a scheduled Cloud Run Job.
    -   Reads workflow event records from BigQuery.
    -   For relevant workflow runs, it uses the GitHub API to download the associated logs.
    -   Stores these logs in Google Cloud Storage (GCS) for long-term archival and analysis.

#### 4. Review Job

-   **CLI Command:** `job review`
-   **Purpose:** This is a compliance and reporting job that verifies commits have undergone a proper review process.
-   **Logic:**
    -   Runs as a scheduled Cloud Run Job.
    -   Reads commit data from BigQuery.
    -   Uses the GitHub API to check the pull request and review status associated with each commit.
    -   (Further actions, like reporting or storing compliance status, would be implemented here).
